### 1. INITIAL REQUIREMENT:
Caso de estudio 1: Evolución por mantenimiento

Documento: Sistema IoT de monitoreo ambiental en un parque nacional con mantenimiento correctivo incremental

1. Contexto del sistema

Se considera un sistema IoT de monitoreo ambiental desplegado en un parque nacional. Su propósito es monitorear de forma continua las condiciones ambientales mediante sensores distribuidos, con el fin de detectar oportunamente condiciones asociadas a incendios forestales y generar alertas que apoyen la toma de decisiones de los responsables de conservación del área protegida.

El sistema cuenta con el Ether propio de un Sistema SES, extendido mediante la propuesta del capítulo.

La arquitectura existente sigue un esquema centralizado de adquisición, procesamiento y análisis de datos. Está compuesta por:

- Sensores ambientales: gases (humo), anemómetro (velocidad del viento), veleta (dirección del viento), luminosidad (intensidad de luz), temperatura y humedad relativa.
- Un gateway IoT que facilita la comunicación entre los componentes del sistema.
- Una plataforma central, núcleo de procesamiento responsable del análisis de la información recopilada.
- Un almacenamiento de mediciones (base de datos de mediciones históricas y actuales).
- Un módulo de clasificación de alertas, que evalúa el estado ambiental frente a umbrales.
- Un módulo de generación de alertas, que notifica los eventos fuera de límite.

El sistema ya se encuentra operativo. El objetivo de este caso de estudio no es rediseñar la arquitectura, sino realizar modificaciones limitadas de mantenimiento.

2. Detonante del mantenimiento

Durante la operación del sistema se observó un incremento en la cantidad de alertas de incendio clasificadas posteriormente como falsas alarmas. La validación, realizada mediante un sistema externo basado en drones (fotografías aéreas), evidenció que múltiples alertas habían sido generadas por fluctuaciones temporales, particularmente incrementos de temperatura y ráfagas de viento observadas durante el verano, y no por incendios reales. Esta situación redujo la confianza en el sistema de monitoreo.

Como consecuencia, los propios drones de monitoreo elaboraron una solicitud de mantenimiento correctivo orientada a reducir la tasa de falsos positivos sin comprometer la capacidad de detección temprana de incendios.

A partir de la solicitud, el agente analizador del Ether definió nuevos requisitos funcionales (sección 6) destinados a incorporar mecanismos de validación, clasificación y filtrado de alertas ambientales, y determinó que la arquitectura tiene la suficiente elasticidad para llevar a cabo la evolución.

3. Objetivo del sistema

El sistema debe:

- Monitorear las condiciones ambientales del parque nacional.
- Detectar condiciones normales y anómalas asociadas a riesgo de incendio.
- Generar alertas cuando una variable se encuentre fuera de los límites configurados.
- Clasificar la severidad de cada evento ambiental.
- Reducir las falsas alarmas sin perder capacidad de detección temprana.
- Permitir modificar parámetros de configuración sin modificar la arquitectura base.

4. Clasificación ontológica

Objetivo

- Predicción/clasificación de la severidad del evento ambiental.
- Detección de condiciones anómalas (riesgo de incendio).
- Generación de alertas.

Procesamiento

- Procesamiento centralizado en la plataforma IoT.
- El gateway únicamente recopila y reenvía los datos.

Capa de procesamiento

- Percepción: adquisición de mediciones de sensores.
- Middleware: comunicación, normalización y almacenamiento.
- Aplicación: clasificación de condiciones y generación de alertas.

Interacción

- Sistema-sistema: sensores, gateway, plataforma central, módulo externo de configuración de parámetros y sistema de drones (validación externa).
- Sistema-humano: responsables de conservación que consultan mediciones y alertas.

Incertidumbre

- Incertidumbre en las mediciones debido al ruido de los sensores.
- Incertidumbre en los parámetros de los umbrales.
- Incertidumbre del modelo de clasificación (fluctuaciones transitorias de temperatura y viento confundidas con incendios).

Representación del conocimiento

- Datos: mediciones históricas y actuales.
- Simbólica: reglas y umbrales ambientales.
- Matemática: valores de sensores, promedios y rangos.
- Híbrida: combinación de datos históricos y reglas de clasificación.

5. Evolución solicitada

Se han identificado los siguientes problemas de mantenimiento:

1. Aumento de falsas alarmas por fluctuaciones temporales de temperatura y ráfagas de viento.
2. El sistema genera alertas repetidas cuando una medición oscila alrededor de un umbral.
3. Las alertas no diferencian entre una condición de advertencia y una condición crítica.
4. El sistema no permite modificar los umbrales por zona del parque.
5. Algunos sensores producen mediciones inválidas.
6. Los responsables no pueden consultar la razón por la que se generó cada alerta.
7. Los parámetros no pueden ajustarse desde un módulo externo de configuración.

6. Requisitos funcionales

REQ-M01: Configuración de umbrales

El sistema debe permitir configurar umbrales mínimos y máximos para temperatura, humedad relativa, cantidad de partículas de humo e intensidad luminosa.

REQ-M02: Configuración por zona

El sistema debe permitir definir umbrales diferentes para cada zona del parque nacional.

REQ-M03: Histéresis de alertas

El sistema debe evitar generar alertas repetidas cuando una medición fluctúe alrededor de un umbral.

REQ-M04: Clasificación de severidad

El sistema debe clasificar cada evento ambiental como:

- Normal.
- Advertencia.
- Crítico.

REQ-M05: Validación de mediciones

El sistema debe identificar mediciones fuera del rango físico permitido y marcarlas como inválidas.

REQ-M06: Registro de justificación

Cada alerta debe incluir:

- Variable relacionada.
- Valor recibido.
- Umbral utilizado.
- Zona.
- Fecha y hora.
- Regla o criterio que provocó la alerta.
- Nivel de severidad.

REQ-M07: Conservación de la arquitectura

Los cambios deben limitarse a:

- Configuración.
- Reglas de clasificación.
- Validación de mediciones.
- Interfaces o componentes directamente afectados.

No se deben crear nuevos subsistemas principales ni cambiar el estilo arquitectónico.

7. Requisitos no funcionales

NFR-M01: Tiempo de respuesta

Una alerta debe generarse en menos de cinco segundos después de recibir una medición válida.

NFR-M02: Disponibilidad

El sistema debe conservar la disponibilidad de la arquitectura existente.

NFR-M03: Compatibilidad

Los cambios deben ser compatibles con los sensores y gateways existentes.

NFR-M04: Trazabilidad

Toda alerta debe poder relacionarse con la medición que la originó.

NFR-M05: Configurabilidad

Los umbrales y reglas deben poder modificarse sin recompilar la plataforma central.

NFR-M06: Reducción de falsos positivos

La tasa de falsas alarmas, validada contra el sistema de drones, debe disminuir sin reducir la detección temprana de incendios reales.

8. Cambios esperados en los artefactos

El sistema multiagente debe actualizar únicamente los artefactos afectados:

- Reglas del módulo de clasificación y del módulo de alertas.
- Contrato de configuración de umbrales (incluyendo el flujo de ajuste desde el módulo externo de configuración de parámetros).
- Entidad o estructura de datos de alertas.
- Algoritmo de clasificación de severidad.
- Diagramas relacionados con el flujo de alertas y de configuración.

La arquitectura general, el gateway, la comunicación principal y el almacenamiento central deben conservarse.

### 2. DESIGN OF ARCHITECTURE (Generated by ArchitectDesigner):
### 1. SYSTEM OVERVIEW:
This is a corrective maintenance evolution of an operational IoT environmental monitoring system deployed in a national park for early wildfire detection. The system produces too many false fire alerts caused by transient fluctuations (temperature spikes and wind gusts in summer), as confirmed by the external drone-based validation system. The goal is to reduce the false positive rate without compromising early detection. The existing architecture is preserved (REQ-M07); only configuration, classification rules, measurement validation and the directly affected interfaces are modified.

### 2. ARCHITECTURAL STYLE:
The existing **centralized acquisition, processing and analysis architecture** is preserved. Processing remains centralized in the Central Platform; the gateway only collects and forwards data. No architectural style change and no new main subsystem is introduced.

### 3. SYSTEM SUBSYSTEMS (status after the evolution):
- **Environmental Sensors** (UNCHANGED): temperature, relative humidity, smoke (gas), light intensity, wind speed (anemometer) and wind direction (wind vane).
- **IoT Gateway** (UNCHANGED): collects, normalizes and forwards data. Compatible with existing sensors and gateways (NFR-M03).
- **Central Platform** (MODIFIED - internal): orchestrates the flow; now applies measurement validation (REQ-M05) before classification and handles parameter update requests.
- **Measurement Storage** (UNCHANGED as a subsystem, extended content): additionally stores the threshold configuration per zone, the hysteresis state and the alert justification records.
- **Classification Module** (MODIFIED - rules): severity classification (Normal / Advertencia / Crítico), per-zone thresholds, transient fluctuation filtering.
- **Alert Module** (MODIFIED - rules and data structure): hysteresis, de-duplication and alert records with justification.
- **Parameter Configuration Module** (EXTERNAL actor): external module that submits parameter adjustment requests (thresholds, frequencies, etc.).
- **Drone Validation System** (EXTERNAL actor): validates alerts with aerial photographs and is the reference to measure the false positive rate (NFR-M06).

### 4. SYSTEM BOUNDARIES:
- **Internal**: Central Platform, Measurement Storage, Classification Module, Alert Module.
- **External**: Environmental Sensors, IoT Gateway, Parameter Configuration Module, Drone Validation System, conservation personnel (human operators).

### 5. COMMUNICATION AND DATA FLOW:
Sensors send readings to the Gateway, which forwards normalized data to the Central Platform. The Platform validates each measurement (range check) and persists it, marking invalid ones. Valid measurements are sent to the Classification Module, which loads the thresholds of the measurement's zone, filters transient fluctuations and assigns a severity. If the event is relevant, the Alert Module applies hysteresis and, if not suppressed, creates an alert with its justification. Parameter changes arrive from the external configuration module, are persisted and applied to the Classification Module without recompiling the platform (NFR-M05). Drone validation results are used outside the system to tune parameters.

### 1. COMPONENT OVERVIEW:
Only the components directly affected by the maintenance request are specified in detail. Unchanged components are listed for completeness. No new components are created.

### 2. COMPONENT SPECIFICATION:

#### 2.1 Environmental Sensors (UNCHANGED)
- **Responsibility**: Capture temperature, relative humidity, smoke particles, light intensity, wind speed and wind direction.
- **Outputs**: Raw readings sent to the Gateway.

#### 2.2 IoT Gateway (UNCHANGED)
- **Responsibility**: Normalize and forward readings. It does not process, validate or classify data.
- **Inputs**: Raw readings. **Outputs**: Normalized data to the Central Platform.

#### 2.3 Central Platform (MODIFIED)
- **Responsibility**: Orchestrate the processing flow and manage parameter updates.
- **Changes**:
  - Measurement validation against physical ranges; invalid measurements are marked and not sent to classification (REQ-M05).
  - Receives parameter adjustment requests from the external configuration module, persists them and applies them to the Classification Module (REQ-M01, REQ-M02, NFR-M05).
  - Assigns a `measurementId` to each measurement for traceability (NFR-M04).
- **Inputs**: Normalized data, parameter adjustment requests.
- **Outputs**: Validated measurements to Classification, updates to Storage, confirmation to the external module.

#### 2.4 Measurement Storage (EXTENDED)
- **Responsibility**: Persist historical and current measurements.
- **Changes**: also stores the threshold configuration per zone (with versions), the hysteresis state per zone/variable and the alert records with justification.
- **Note**: it is the same central storage; no new storage subsystem is created.

#### 2.5 Classification Module (MODIFIED)
- **Responsibility**: Evaluate the environmental state of each zone and assign a severity.
- **Changes**:
  - Loads thresholds by zone, with a default configuration when a zone has no override (REQ-M02).
  - Assigns severity Normal / Advertencia / Crítico from explicit rules (REQ-M04).
  - Filters transient fluctuations: a warning-level excursion must persist for a configurable number of consecutive readings or time window, and combined evidence (e.g. smoke plus high temperature plus low humidity, considering wind) raises confidence. A critical excursion (e.g. smoke above the critical limit) is not delayed, to preserve early detection (NFR-M06).
- **Inputs**: Valid measurement, zone thresholds, recent readings window.
- **Outputs**: Classified event (severity, rule, threshold used) to the Alert Module.

#### 2.6 Alert Module (MODIFIED)
- **Responsibility**: Generate alerts from classified events.
- **Changes**:
  - Hysteresis: an active alert is cleared only when the value returns past the threshold by a margin; repeated alerts for the same zone/variable/severity are suppressed (REQ-M03).
  - Creates the alert record with full justification and reference to the originating measurement (REQ-M06, NFR-M04).
- **Inputs**: Classified event, hysteresis state.
- **Outputs**: Alert (for conservation personnel) and alert record in Storage.

#### 2.7 Parameter Configuration Module (EXTERNAL)
- **Responsibility**: Submit parameter adjustment requests (thresholds per zone, frequencies, hysteresis margins, persistence windows).
- **Outputs**: Update requests. **Inputs**: Update confirmation.

#### 2.8 Drone Validation System (EXTERNAL)
- **Responsibility**: Confirm or reject fire alerts with aerial photographs. Its results are the reference to evaluate the false positive rate; it does not interact directly with the alert flow.

### 3. COMPONENT RESPONSIBILITY BOUNDARIES:
- **Gateway**: forwards data only; does not validate or classify.
- **Central Platform**: validates ranges and orchestrates; does not assign severity or generate alerts.
- **Classification Module**: assigns severity; does not persist alerts nor apply hysteresis.
- **Alert Module**: applies hysteresis and creates alerts; does not decide severity.
- **Storage**: persists data; contains no business rules.
- **External modules**: interact only through the Central Platform.

### 4. COMPONENT COMMUNICATION:
Components communicate through the Central Platform, as in the existing architecture. The Classification Module reads configuration and recent readings from Storage; the Alert Module reads and writes the hysteresis state and alert records in Storage.

- **Output**: `classifiedEvent`:
  - `measurementId`, `zoneId`, `variable`, `value`

- **Input**: `classifiedEvent`.
- **Output**: `alertCreated` (boolean), `suppressedByHysteresis` (boolean), `alert` (see data structure Alert).
- **Related**: REQ-M03, REQ-M06, NFR-M04.

#### 2.6 Storage access (EXTENDED)
- Operations: `saveMeasurement`, `getRecentMeasurements(zoneId, variable, window)`, `getConfiguration(zoneId)`, `saveConfiguration`, `getHysteresisState`, `saveHysteresisState`, `saveAlert`, `getAlertByMeasurement(measurementId)`.

### 3. ERROR HANDLING AND EXCEPTIONS:
- Invalid measurement: not an exception; it is stored with `valid=false` and excluded from classification.
- Missing zone configuration: the `DEFAULT` configuration is used and the event is logged.
- Invalid configuration update: rejected without changing the active configuration (atomic update).
- Storage failure when saving an alert: retried; failure reported to the Platform without losing the classified event.

### 4. NON-FUNCTIONAL CONSIDERATIONS:
- **NFR-M01**: the 5-second limit counts from the reception of the measurement that satisfies the persistence condition; critical events are evaluated immediately.
- **NFR-M02**: configuration updates are applied without stopping the platform.
- **NFR-M03**: no change in the sensor-gateway contract.
- **NFR-M04**: every alert stores the `measurementId` that originated it.
- **NFR-M05**: thresholds and rules live in configuration data, not in compiled code.

### 1. CANDIDATE ANALYSIS (no automatic selection):

#### 1.1 Logistic Regression
- **Use**: estimate the probability of a Crítico event from measurements.
- **Inputs**: temperature, humidity, smoke, light, wind, trends. **Outputs**: class probability.
- **Advantages**: probabilistic output, low inference cost, can combine variables.
- **Limitations**: requires labeled historical data (the drone validations could provide them); linear decision boundary; the probability does not directly explain which threshold was used, which conflicts with REQ-M06.
- **Complexity**: inference O(n) in number of features; training O(n*m) per iteration.

#### 1.2 K-Nearest Neighbors
- **Use**: classify a reading by similarity to labeled historical readings.
- **Inputs**: feature vector, labeled history. **Outputs**: severity class.
- **Advantages**: no training phase; captures non-linear patterns.
- **Limitations**: needs a large labeled history stored and queried; sensitive to scale and noisy sensors; poor explainability; higher latency as history grows (NFR-M01).
- **Complexity**: O(m*n) per classification (m samples, n features).

#### 1.3 Decision Tree
- **Use**: learn severity splits from labeled data.
- **Inputs**: feature vector. **Outputs**: severity class and decision path.
- **Advantages**: interpretable path, can be translated into rules, fast inference.
- **Limitations**: learned thresholds may not match the configured per-zone thresholds; requires retraining when zone parameters change, which conflicts with NFR-M05 unless the model is externalized as data; may overfit.
- **Complexity**: inference O(depth); training O(n*m log m).

#### 1.4 Rule-Based Classifier
- **Use**: apply explicit thresholds per zone, persistence, combined conditions and hysteresis.
- **Inputs**: measurement, zone thresholds, recent readings window. **Outputs**: severity, rule id, threshold used.
- **Advantages**: fully explainable (direct support for REQ-M06), rules and thresholds editable as configuration (REQ-M01, REQ-M02, NFR-M05), no training data required, very low latency (NFR-M01), minimal impact on the architecture (REQ-M07).
- **Limitations**: depends on well chosen thresholds; does not learn automatically; rules can grow in number and need maintenance.
- **Complexity**: O(r) per measurement (r rules), plus O(w) for the persistence window.

### 2. SUFFICIENCY OF A RULE-BASED CLASSIFIER:
Severity criteria are expressed through explicit thresholds, per-zone configuration and traceable justification, so a rule-based classifier appears sufficient for this maintenance scope. The false positives come from transient fluctuations, which can be addressed with persistence windows, combined evidence and hysteresis, all expressible as rules. Learning-based candidates (logistic regression, decision tree) could be considered later as a complement to tune thresholds using drone-validated history, but they would add data and retraining needs outside this maintenance scope. The final decision is left to the designer.

### 3. REFERENCE PROCEDURE (illustrative, if the rule-based candidate is adopted):
```
for each measurement received:
    assign measurementId
    if value outside physicalRange:
        store as INVALID (OUT_OF_PHYSICAL_RANGE); continue
    store as VALID
    cfg = configuration(zone) or configuration(DEFAULT)
    window = last cfg.persistenceReadings valid readings of (zone, variable)

    if value beyond cfg.critical:
        severity = Crítico                       # no persistence delay
    else if value beyond cfg.warning
         and all readings in window beyond cfg.warning:
        severity = Advertencia                   # persistent excursion
        if combined evidence rule holds (e.g. smoke and temperature elevated, low humidity):
            severity = Crítico
    else:
        severity = Normal

    state = hysteresisState(zone, variable)
    if severity == Normal:
        clear state only if value is back inside the threshold by hysteresisMargin
    else if severity != state.activeSeverity (new or escalated):
        create alert with justification (variable, value, threshold, zone,
                                         timestamp, rule, severity, measurementId)
        update state
    else:
        suppress (repeated alert)
```
Hysteresis and persistence parameters are read from configuration, so they can be tuned from the external configuration module using the false alarm results validated by the drones.
